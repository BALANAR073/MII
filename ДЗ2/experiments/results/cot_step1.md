## 1. Входные данные

**Участники группы (`Member`)**
- `id: string` — стабильный идентификатор.
- `name: string` — нужно только для UI, в расчёте не участвует.
- `joinedOrder: number` или просто позиция в массиве `members`. По этому порядку детерминированно раздаются лишние копейки.
- `leftAt: string | null` — дата выхода из группы. Участника не удаляем физически, иначе сломается история.

**Расходы (`Expense`)**
- `id: string`
- `payerId: string` — кто платил. **[Д]** Плательщик один. Если платили несколько человек, такой расход вносится как несколько отдельных расходов.
- `amountKop: Kopecks` — целое число больше 0.
- `split` — способ деления, размеченное объединение:
  - `{ kind: 'equal', memberIds: string[] }` — поровну между перечисленными;
  - `{ kind: 'shares', shares: { memberId: string; weight: number }[] }` — по долям (2:1:1).
- `createdAt: string` — для сортировки в UI. На результат расчёта не влияет.

**Выполненные переводы (`Transfer`, «погашения»)**
- `id`, `fromId` (кто отдал деньги), `toId` (кто получил), `amountKop > 0`, `createdAt`.

**[Д]** Валюта одна (₽). Мультивалютность в эту версию не входит.

## 2. Выход

1. **Балансы.** Массив `{ memberId, balanceKop }` по всем участникам, включая вышедших.
   - `balanceKop > 0` — участнику должны («вам должны», `text-emerald-600`);
   - `balanceKop < 0` — участник должен («вы должны», `text-rose-600`);
   - `0` — «в расчёте».
   - **Инвариант:** сумма всех `balanceKop` равна 0.
2. **Предлагаемые переводы.** Массив `{ fromId, toId, amountKop }`, после выполнения которого все балансы станут 0. Если все в расчёте, массив пустой.
3. Для UI доли конкретного расхода по участникам нужны отдельно, поэтому функция деления суммы экспортируется сама по себе.

## 3. Правила расчёта

### 3.1. Деление суммы по долям
- Равное деление — частный случай деления по долям: у каждого вес 1. Поэтому реализуется одна функция `splitByWeights`.
- Базовая часть: `floor(amountKop * weight / totalWeight)`. Всё считается в целых числах, без float. Произведение `amountKop * weight` должно оставаться в пределах `Number.MAX_SAFE_INTEGER`, поэтому вводим ограничения на сумму и вес (см. п. 4).
- Остаток: `R = amountKop − Σ base`, причём `0 ≤ R < число участников`.

### 3.2. Куда девать остаток копеек (метод наибольших остатков)
- Каждый из R участников получает по +1 копейке. Порядок:
  1. по убыванию дробного остатка `(amountKop * weight) mod totalWeight`, сравниваются целые числа;
  2. при равенстве — по порядку участника в списке `members` группы.
- Порядок группы берём, а не порядок в конкретном расходе, потому что тогда результат не зависит от того, в какой последовательности участников отметили в форме.
- Пример: 100,00 ₽ (10000 коп) поровну на троих → 3334 / 3333 / 3333. Лишняя копейка уходит первому по порядку группы.
- Пример: 100 коп по долям 2:1:1 → 50 / 25 / 25, остатка нет.
- Пример: 1 коп на троих → 1 / 0 / 0.
- **[Д]** Остаток не отдаётся «плательщику по умолчанию». Правило одно для всех расходов, так его проще объяснить и протестировать.

### 3.3. Баланс участника
```
balance = Σ(оплатил как payer) − Σ(своя доля в расходах)
        + Σ(отправил переводами) − Σ(получил переводами)
```
- Перевод от A к B на X означает, что A погасил часть долга: `balance[A] += X`, `balance[B] −= X`. Сумма балансов при этом не меняется.
- Расходы и переводы суммируются, порядок записей на результат не влияет.
- Перевод больше долга разрешён. Баланс просто меняет знак, и алгоритм предложит обратный перевод. **[Д]** Блокировать такие переводы — задача формы, а не расчёта.

### 3.4. Минимальный список переводов
- Строго минимальное число переводов — NP-трудная задача (сводится к разбиению на подмножества с нулевой суммой). Поэтому:
- **[Д]** Используем жадный алгоритм. На каждом шаге самый крупный должник переводит самому крупному кредитору `min(|долг|, кредит)`. Получается не больше `n − 1` переводов, где n — число участников с ненулевым балансом. На реальных группах результат почти всегда оптимален.
- Предварительный шаг: если у должника и кредитора суммы совпадают точно, сначала закрываем такие пары. Это дёшево и часто экономит перевод.
- Детерминизм: при равных суммах порядок задаётся положением в `members`.
- Все суммы в переводах — целые копейки, это получается автоматически, потому что входные балансы целые.

### 3.5. Участник вышел из группы
- Участник помечается `leftAt`, а не удаляется. Все прошлые расходы и переводы с его участием остаются в силе.
- В расчёте он участвует как обычный участник: его баланс считается и входит в предлагаемые переводы. Иначе нарушится инвариант «сумма = 0».
- UI-правила (это не логика расчёта):
  - выход из группы разрешён только при нулевом балансе, иначе показываем «Сначала рассчитайтесь: вы должны …»;
  - вышедшего нельзя выбрать в новом расходе или переводе;
  - в списке он отображается с пометкой «вышел из группы».
- Если данные всё-таки содержат вышедшего с ненулевым балансом (моки, legacy), расчёт его не теряет и выдаёт переводы с его участием.

## 4. Граничные случаи

**Группа и данные**
1. Нет участников → балансы `[]`, переводы `[]`.
2. Участники есть, расходов и переводов нет → у всех 0, переводы `[]`.
3. Один участник → его баланс всегда 0.
4. Все в расчёте после переводов → переводы `[]`.

**Расход**

5. `amountKop` ≤ 0, дробное, `NaN`, `Infinity` или больше лимита → ошибка валидации. **[Д]** Лимит: 10 000 000 000 коп (100 млн ₽) на расход.
6. Пустой список участников деления → ошибка.
7. Дубли `memberId` в одном расходе → ошибка. Молча склеивать не будем, иначе вес незаметно удвоится.
8. `payerId` или `memberId`, которых нет в группе → ошибка.
9. Вес не целый, ≤ 0 или больше 1000 → ошибка. **[Д]** Вес 0 запрещён: если человек не участвует, его просто не включают в деление.
10. Плательщик не входит в деление (заплатил за других) — допустимо.
11. Плательщик — единственный участник деления → расход на балансы не влияет. Это допустимо: личная трата для истории.
12. Сумма меньше числа участников (1 коп на троих) → 1/0/0, корректно.
13. Сумма делится без остатка → остаток 0, никто не получает лишнюю копейку.
14. Очень большие суммы → проверка безопасного произведения `amountKop × weight`. С лимитами из п. 5 и 9 получаем не больше 10¹³, это меньше 9·10¹⁵.

**Перевод**

15. `fromId === toId` → ошибка.
16. `amountKop` ≤ 0 или нецелый → ошибка.
17. Неизвестный участник → ошибка.
18. Переплата → допустима, см. 3.3.

**Вышедший участник**

19. В старых расходах он есть, в новых его нет → корректно.
20. Его баланс не 0 → он попадает в переводы и помечается в UI.

**Инварианты для тестов**

21. Для любого расхода сумма долей равна `amountKop`.
22. Сумма балансов группы равна 0.
23. После применения предложенных переводов все балансы равны 0.
24. Перестановка расходов или переводов во входных массивах не меняет результат.

## Принятые решения (опора для шагов 2–4)

1. Все суммы — `Kopecks` (целые `number`), поля с суффиксом `Kop`. Без float, `toFixed`, `parseFloat`. Отображение только через `formatRub`.
2. Типы: `Member { id, name, leftAt: string | null }`, `Expense { id, payerId, amountKop, split, createdAt }`, `Transfer { id, fromId, toId, amountKop, createdAt }`. Порядок массива `members` — значимый, по нему разрешаются ничьи.
3. `split` — размеченное объединение `equal | shares`. Равное деление сводится к долям с весом 1, функция деления одна (`splitByWeights`).
4. Остаток копеек раздаётся методом наибольших остатков по одной копейке. При равенстве решает порядок участника в группе. Сумма долей всегда равна сумме расхода.
5. Плательщик у расхода один. Он может не входить в деление.
6. Знак баланса: `> 0` — участнику должны, `< 0` — участник должен. Формула из п. 3.3. Перевод A→B увеличивает баланс A и уменьшает баланс B.
7. Переплата переводом допустима, расчёт её корректно отражает.
8. Список переводов строит детерминированный жадный алгоритм с предварительным закрытием точно совпадающих пар. Гарантия — не больше n−1 переводов. Абсолютный минимум не гарантируется, и это сознательное решение.
9. Вышедший участник — мягкое удаление (`leftAt`). Он полностью участвует в расчёте и переводах. Запрет выхода при ненулевом балансе и запрет выбора в новых записях — правила UI и форм, а не расчётного ядра.
10. Валидация: веса — целые 1…1000, `amountKop` — целое 1…10¹⁰. Пустое деление, дубли, неизвестные id и перевод самому себе — ошибки.
11. Ошибки возвращаются как результат, а не исключение: `{ ok: true, balances, transfers } | { ok: false, errors: ValidationError[] }`, где у ошибки есть код, id записи и текст на русском. Так UI может показать состояние ошибки без try/catch.
12. Размещение (уточним на шаге 2):
    - `src/types/` — доменные типы;
    - `src/lib/money.ts` — `Kopecks`, `formatRub`;
    - `src/lib/splitByWeights.ts`;
    - `src/features/balances/` — `calculateBalances`, `suggestTransfers`, `validateGroupData`, затем хук `useGroupBalances` и компоненты.
    
    Логика без React, к каждой функции — тест с позитивным и граничным сценарием.
13. Тексты в UI: «вам должны», «вы должны», «в расчёте», «вышел из группы». Знак долга не передаётся только цветом.
