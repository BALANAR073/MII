# ДЗ2. Библиотека промпт-шаблонов (Шаг 3)

**Выполнил:** Творогов Д.Н., гр. 4481
**Агент:** Claude Code (правила проекта подгружаются из `CLAUDE.md`)

Все шаблоны построены по структуре **RTCF**:
- **Role (Роль)** — кем является AI в этом контексте;
- **Task (Задача)** — что конкретно нужно сделать;
- **Context (Контекст)** — какая информация нужна для решения;
- **Format (Формат)** — в каком виде нужен результат.

Значения в фигурных скобках `{…}` заменяются при использовании. Общие правила проекта (стек, стиль, запреты) уже есть в `CLAUDE.md`, поэтому в шаблонах они не повторяются. Шаблон задаёт только то, что специфично для задачи.

| № | Шаблон | Когда использовать |
|:-:|---|---|
| 1 | Генерация компонента / функции | новый код по описанию |
| 2 | Рефакторинг | улучшить существующий код без изменения поведения |
| 3 | Написание тестов | покрыть тестами готовый код |
| 4 | Исправление бага | есть ошибка, стектрейс или неверное поведение |
| 5 | Декомпозиция задачи | большая фича, которую нужно разбить на шаги для агента |

## Шаблон 1. Генерация компонента / функции

```markdown
**Role:** Ты — Senior Frontend-разработчик проекта «ПоРовну».

**Task:** Создай {компонент | функцию | хук} `{Имя}`, который {что делает — одним предложением}.

**Context:**
- Где используется: {страница / родительский компонент}
- Входные данные: {props / аргументы с типами}
- Поведение: {список требований, по пункту на строку}
- Граничные случаи: {пустые данные, ошибки, крайние значения}
- Связанные файлы: {@путь/к/типам, @путь/к/похожему компоненту}

**Format:**
- файл `{путь}` и тест `{путь}.test.tsx`;
- перед кодом — 2–3 строки: принятые решения и допущения;
- в конце — команда проверки.
```

### Пример использования

```markdown
**Role:** Ты — Senior Frontend-разработчик проекта «ПоРовну».

**Task:** Создай компонент `ExpenseCard`, который показывает один расход в ленте группы.

**Context:**
- Где используется: список расходов на странице GroupPage
- Входные данные: expense: Expense (id, title, amountKop, payerId, participantIds, date,
  category), members: Member[], currentUserId: string
- Поведение: название и категория-иконка; сумма через formatRub; «Платил: Аня»
  (или «Вы заплатили»); «Делится на 3 человек»; доля текущего пользователя:
  «Ваша доля 333,34 ₽» или «Вы не участвуете»
- Граничные случаи: остаток копеек при делении; плательщик не участвует в расходе;
  участник удалён из группы — показать «Бывший участник»
- Связанные файлы: @src/types/expense.ts, @src/lib/money.ts

**Format:**
- файл `src/features/expenses/ExpenseCard.tsx` и тест `ExpenseCard.test.tsx`;
- перед кодом — принятые решения;
- в конце — команда проверки.
```

**Ожидаемый результат:** типизированный компонент; доля считается чистой функцией из `lib/` в копейках, а не в компоненте; правильное склонение «человек/человека»; тесты на 100 ₽ на троих и на «вы не участвуете».

## Шаблон 2. Рефакторинг кода

```markdown
**Role:** Ты — Senior-разработчик, проводящий рефакторинг. Главное правило: поведение
кода не должно измениться.

**Task:** Отрефактори `{файл или функция}` с целью: {читаемость | производительность |
разделение ответственности | типизация}.

**Context:**
- Текущий код: {@путь или вставка кода}
- Что не нравится: {конкретные проблемы: длинная функция, дублирование, логика в компоненте…}
- Что нельзя менять: {публичный API / props / формат данных}
- Существующие тесты: {@путь к тестам или «тестов нет»}

**Format:**
1. Список проблем (маркированный, по одной строке).
2. План изменений.
3. Новый код файлов целиком.
4. Подтверждение, что тесты проходят без изменений; если тестов нет — сначала напиши тесты
   на текущее поведение.
```

### Пример использования

```markdown
**Role:** Ты — Senior-разработчик, проводящий рефакторинг. Главное правило: поведение
кода не должно измениться.

**Task:** Отрефактори `GroupPage.tsx` с целью разделения ответственности.

**Context:**
- Текущий код: @src/pages/GroupPage.tsx
- Что не нравится: компонент на 250 строк — загрузка данных, фильтр по категориям,
  расчёт балансов и разметка в одном месте; расчёт балансов дублирует src/lib/settle.ts
  и делает это во float
- Что нельзя менять: маршрут /groups/:id, внешний вид страницы
- Существующие тесты: @src/pages/GroupPage.test.tsx

**Format:** список проблем → план → новый код → результат npm test.
```

**Ожидаемый результат:** загрузка вынесена в хук `useGroup`, фильтрация — в чистую функцию, дубль расчёта заменён на `lib/settle.ts` в копейках, страница стала короче, тесты зелёные.

## Шаблон 3. Написание тестов

```markdown
**Role:** Ты — QA-инженер / разработчик тестов (Vitest + React Testing Library).

**Task:** Напиши тесты для `{файл / функция / компонент}`.

**Context:**
- Код для тестирования: {@путь}
- Что важно проверить: {ключевое поведение}
- Известные граничные случаи: {список}
- Что мокать: {API, дата «сегодня», таймеры} / «ничего»

**Format:**
- файл `{путь}.test.ts(x)`;
- тесты сгруппированы через describe: «позитивные сценарии», «граничные случаи», «ошибки»;
- названия тестов на русском в виде «должен …»;
- тестировать поведение (что видит пользователь), а не внутреннюю реализацию;
- запусти тесты и приведи итог (сколько прошло).
```

### Пример использования

```markdown
**Role:** Ты — QA-инженер / разработчик тестов (Vitest + React Testing Library).

**Task:** Напиши тесты для функции `splitByShares` (деление расхода по долям, например 2:1:1).

**Context:**
- Код для тестирования: @src/features/expenses/lib/split.ts
- Что важно проверить: сумма частей всегда равна исходной сумме до копейки
- Известные граничные случаи: 100 ₽ в пропорции 1:1:1; доля 0 у участника; одна копейка
  на троих; очень большая сумма; отрицательная или дробная доля
- Что мокать: ничего, функция чистая

**Format:** describe-группы, названия «должен …», итог запуска.
```

**Ожидаемый результат:** 8–12 тестов, включая «1 копейка на троих → 1 + 0 + 0»; найденные расхождения агент описывает отдельно, а не «подгоняет» тест под код.

## Шаблон 4. Исправление ошибки / бага

```markdown
**Role:** Ты — опытный разработчик, который ищет первопричину, а не маскирует симптомы.

**Task:** Найди и исправь ошибку: {краткое описание}.

**Context:**
- Ожидаемое поведение: {…}
- Фактическое поведение: {…}
- Как воспроизвести: {шаги}
- Сообщение об ошибке / стектрейс / вывод консоли: {вставка}
- Подозрительный код: {@путь}
- Окружение: {браузер, часовой пояс, версия Node — если важно}

**Format:**
1. Причина ошибки — 2–3 предложения.
2. Исправленный код (только изменённые файлы).
3. Регрессионный тест, который падал до исправления и проходит после.
4. Не трогай код, не связанный с ошибкой.
```

### Пример использования

```markdown
**Role:** Ты — опытный разработчик, который ищет первопричину, а не маскирует симптомы.

**Task:** Найди и исправь ошибку: после всех переводов у участника остаётся долг «0,00 ₽».

**Context:**
- Ожидаемое поведение: после выполнения всех переводов из settleDebts балансы равны 0
- Фактическое поведение: баланс Бори -0.15000000000000002 вместо -0.15,
  у «100 ₽ на троих» сумма балансов -1.42e-14
- Как воспроизвести: npm test (тесты «100 ₽ на троих», «0.10 + 0.20 ₽»)
- Сообщение об ошибке: AssertionError: Expected values to be strictly equal:
  -1.4210854715202004e-14 !== 0
- Подозрительный код: @src/lib/settle.ts
- Окружение: Node 22

**Format:** причина → исправление → регрессионный тест.
```

**Ожидаемый результат:** причина — денежные суммы во float (`0.1 + 0.2 !== 0.3`, 100/3 не делится); исправление — перевод в целые копейки с детерминированной раздачей остатка; регрессионные тесты на копейки. Это реальная ошибка из ДЗ1.

## Шаблон 5. Декомпозиция сложной задачи

```markdown
**Role:** Ты — техлид, который планирует работу для AI-агента и разработчиков.

**Task:** Разбей задачу «{название фичи}» на подзадачи, каждую из которых можно выполнить
одним промптом и проверить отдельно.

**Context:**
- Описание фичи: {что должен получить пользователь}
- Что уже есть в проекте: {модули, компоненты, API}
- Ограничения: {сроки, без новых зависимостей, mock-данные вместо API…}
- Критерии готовности фичи: {…}

**Format:**
Таблица: № | Подзадача | Входные данные | Результат (файлы) | Как проверить | Зависит от.
Подзадачи упорядочены так, чтобы каждая опиралась на уже готовые.
После таблицы — риски и вопросы, которые нужно уточнить до начала.
Код не писать.
```

### Пример использования

```markdown
**Role:** Ты — техлид, который планирует работу для AI-агента и разработчиков.

**Task:** Разбей задачу «Экран „Рассчитаться“» на подзадачи, каждую из которых можно выполнить
одним промптом и проверить отдельно.

**Context:**
- Описание фичи: пользователь открывает группу, видит, кому и сколько должен перевести
  (минимальный список переводов), может отметить перевод выполненным — балансы
  пересчитываются, перевод попадает в историю
- Что уже есть в проекте: lib/settle.ts (calculateBalances, settleDebts, formatRub),
  типы Expense и Member, mock-данные
- Ограничения: без новых зависимостей, бэкенда пока нет (состояние в памяти)
- Критерии готовности фичи: после отметки всех переводов все балансы 0, адаптивность, тесты

**Format:** таблица подзадач → риски и вопросы. Код не писать.
```

**Ожидаемый результат:** 5–7 подзадач (тип Settlement → учёт выполненных переводов в балансах → тесты → хук `useSettleUp` → компоненты → страница), вопросы вида «можно ли отметить перевод частично» и «кто может отмечать перевод — плательщик или получатель».

## Как пользоваться библиотекой

1. Выбрать шаблон по таблице в начале файла.
2. Заполнить `{…}`. Чем конкретнее граничные случаи и контекст, тем меньше итераций.
3. Подключать файлы через `@путь`, а не вставлять код вручную: Claude Code сам прочитает актуальную версию.
4. Для больших задач сначала использовать шаблон 5, а затем выполнять подзадачи шаблоном 1, по шагам (см. `prompt_methodology.md`).
