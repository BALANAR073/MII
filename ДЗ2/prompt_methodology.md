# ДЗ2. Применение техники Chain-of-Thought (Шаг 4)

**Выполнил:** Творогов Д.Н., гр. 4481
**Агент:** Claude Code 2.1.301 (модель Opus 5.5), правила проекта из `CLAUDE.md`

## Задача

**Модуль «Кто кому должен»** для экрана группы в «ПоРовну». По расходам группы и уже выполненным переводам нужно посчитать баланс каждого участника и минимальный список переводов, после которых все в расчёте. Расход делится поровну или по долям (2:1:1).

Почему задача сложная и подходит для CoT:
- много неочевидных решений: куда девать копейки при делении 2:1:1, как учитывать выполненные переводы, что делать с участником, вышедшим из группы;
- минимизация числа переводов — NP-трудная задача, нужен осознанный компромисс;
- если сразу просить код, агент молча примет решения сам, и потом их трудно проверить.

## Как применялась техника

Задача разбита на **4 логических шага**: анализ → контракт → реализация → тесты и самопроверка. Каждый шаг — отдельный промпт. Агент сначала рассуждает и фиксирует решения, а каждый следующий шаг опирается на результат предыдущего.

Технически цепочка выполнялась одним продолжающимся диалогом: первый вызов `claude -p`, следующие — `claude -c -p` (флаг `-c` продолжает последний диалог в папке). Запуск автоматизирован скриптом `experiments/run_experiments.ps1`, все сырые ответы сохранены в `experiments/results/cot_step1.md` … `cot_step4.md`.

```
Шаг 1. Анализ          → список из 13 решений и 24 граничных случаев (без кода)
   ↓ опирается на решения
Шаг 2. Контракт        → типы TypeScript и сигнатуры функций с JSDoc (без реализации)
   ↓ реализует сигнатуры
Шаг 3. Реализация      → 9 функций + mock-данные + 43 теста
   ↓ проверяет по списку шага 1
Шаг 4. Тесты и самопроверка → 35 тестов на граничные случаи, сверка 13 решений, 2 исправления
```

## Шаг 1. Анализ (66 с)

**Промпт:**
```text
Задача: модуль «Кто кому должен» для экрана группы в приложении «ПоРовну». По списку расходов группы и уже выполненных переводов нужно посчитать баланс каждого участника и минимальный список переводов, после которых все в расчёте. Расход может делиться поровну или по долям (например, 2:1:1).

Решаем по шагам. Это шаг 1 из 4 — анализ. Код пока НЕ пиши.
Рассуждай последовательно:
1) какие входные данные нужны (участники, расходы, выполненные переводы);
2) что должно получиться на выходе;
3) правила расчёта: как делить сумму по долям, куда девать остаток копеек, как учитывать уже выполненные переводы, что делать с участником, который вышел из группы;
4) все граничные случаи.
В конце дай пронумерованный список принятых решений — на него будем опираться в следующих шагах.

Не создавай и не изменяй файлы — отвечай текстом.
```

**Результат** (`cot_step1.md`): агент рассуждал по четырём пунктам и выдал:
- **входные данные:** `Member` (с мягким удалением `leftAt`), `Expense` с размеченным объединением `split: equal | shares`, `Transfer`;
- **правило копеек:** метод наибольших остатков, при равенстве — по порядку участника в группе. Пример: 1 копейка на троих → 1 / 0 / 0;
- **формулу баланса** с учётом выполненных переводов и допустимость переплаты;
- **осознанный компромисс:** точная минимизация переводов — NP-трудная задача, поэтому выбран жадный алгоритм, который даёт не больше n−1 переводов;
- **24 граничных случая**, сгруппированных по темам (группа, расход, перевод, вышедший участник, инварианты);
- **13 пронумерованных решений** — опору для следующих шагов — и 3 вопроса к заказчику.

Все допущения агент пометил **[Д]**. Это прямое следствие правила 1 из `CLAUDE.md`.

## Шаг 4. Тесты и самопроверка (192 с)

**Промпт:**
```text
Шаг 4 из 4 — тесты и самопроверка.
1) Напиши тесты Vitest для функций из шага 3: минимум по одному тесту на каждый граничный случай из шага 1.
2) Проведи самопроверку: пройди по списку решений и граничных случаев из шага 1 и для каждого укажи, где и как он обработан в реализации.
3) Если нашёл расхождение или ошибку — объясни её и выведи исправленный код.

Не создавай и не изменяй файлы — выведи код в ответе.
```

**Результат** (`cot_step4.md`):
1. Файл `balances.edgeCases.test.ts`: **по тесту на каждый из 24 граничных случаев** шага 1, всего 35 проверок.
2. **Таблица самопроверки:** все 13 решений и 24 граничных случая из шага 1, у каждого указано, где он обработан.
3. **Найдены и исправлены 2 расхождения:**
   - решение 9 («выйти из группы можно только с нулевым балансом») нигде не было реализовано. Добавлена чистая функция `canLeaveGroup` и 3 теста к ней;
   - в одном тесте вывод типа `new Map(...)` был хрупким для `strict`. Добавлены явные параметры типа.
4. Агент честно записал одно **известное ограничение**: переполнение при обороте группы больше 9·10¹⁵ копеек. Он объяснил, почему сейчас его не исправляет.

## Выводы

1. **CoT дал проверяемый ход решения.** Все неочевидные решения (копейки, переплаты, вышедшие участники, компромисс с жадным алгоритмом) зафиксированы на шаге 1 до появления кода. Их можно обсудить и поправить, не переписывая реализацию.
2. **Шаги действительно опираются друг на друга.** Шаг 2 явно уточняет решения шага 1, шаг 4 сверяет реализацию с пронумерованными списком решений и граничных случаев шага 1. Без такой опоры самопроверку не на что было бы ссылаться.
3. **Самопроверка нашла пропуск, который легко не заметить:** правило выхода из группы было объявлено, но не реализовано. При генерации «одним промптом» такая потеря не видна.
4. **Цена:** около 9,5 минуты работы агента и примерно 100 КБ ответов. Для небольшой функции это избыточно, но для модуля с денежной логикой и десятком функций оправдано: результат прошёл 81 тест и строгую проверку типов без единой правки.

**Рекомендация:** для сложных задач сначала просить анализ и список решений без кода (шаг 1). Этот список использовать как контракт для последующих шагов, а последний шаг всегда делать самопроверкой по нему.
