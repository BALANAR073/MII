Все промпты построены по шаблону RTCF из ДЗ2 (Role — Task — Context — Format). Правила проекта агент берёт из `poravnu/CLAUDE.md`, поэтому в промптах их не повторяем. Первый раздел — промпты, которые в ДЗ4 реально отправлялись агенту на ПК, дословно. Остальные разделы — шаблоны для повторяющихся задач: в них заменяется только содержимое в угловых скобках.

### 1.2. AI-ревью кода (`review/code_review_prompt.txt`)

```text
Role: ты — senior frontend-ревьюер (React 18 + TypeScript strict + Tailwind) с опытом в доступности
и финансовых интерфейсах.
Task: проведи код-ревью папки poravnu/src. Проверь: 1) нарушения правил проекта из poravnu/CLAUDE.md;
2) ошибки логики и обработку ошибок; 3) доступность; 4) адаптивность (360–1440 px);
5) производительность и лишние перерисовки; 6) структуру кода и читаемость; 7) качество тестов.
Сверяйся с требованиями ../ДЗ3/technical_specification.md.
Context: это MVP «ПоРовну» на mock-API, бэкенд Supabase будет в ДЗ5. Код написан AI-агентом
и уже прошёл 115 автотестов, проверку типов и визуальную отладку по скриншотам.
Format: 1) таблица находок: № | файл:строка | категория | проблема | серьёзность | как исправить;
2) что сделано хорошо; 3) три самых важных исправления; 4) оценка по 10-балльной шкале.
Файлы не изменяй — только ответ.
```

Результат: `ai_code_review.md`, 31 находка, оценка 7 / 10. Разбор — `ai_code_review_response.md`.

## 2. Адаптивность — частые проблемы

### 2.1. Баг вёрстки по скриншоту

```text
Role: ты — frontend-разработчик, специалист по адаптивной вёрстке на Tailwind.
Task: на скриншоте <файл.png> (ширина <360> px) <что не так: «название группы обрезано многоточием»>.
Найди причину в <компонент.tsx> и исправь так, чтобы на <360, 768, 1280> px текст помещался.
Context: mobile-first, брейкпоинты Tailwind sm/lg/xl, inline-стили запрещены (правило 17).
Format: причина в одном предложении → изменённый фрагмент кода с путём → как проверить на каждой ширине.
```

### 2.2. Горизонтальная прокрутка

```text
Role: ты — frontend-разработчик.
Task: на ширине <360> px у страницы <адрес> появляется горизонтальная прокрутка
(document.documentElement.scrollWidth = <412> > innerWidth = <360>). Найди элемент, который вылезает
за экран, и исправь.
Context: частые причины — flex-элемент без min-w-0, длинные строки без truncate/break-words,
фиксированная ширина, отрицательные отступы.
Format: селектор виновника → причина → исправление → проверка scrollWidth ≤ innerWidth.
```

### 2.3. Раскладка под брейкпоинты

```text
Role: ты — UI-инженер.
Task: спроектируй раскладку экрана <«Группа»> для 360, 768, 1024, 1280 и 1440 px: сколько колонок,
ширины колонок, что скрывается или переезжает. Минимальная ширина основной колонки — <560> px.
Context: макет — <концепция>, на телефоне вкладки «Расходы | Балансы», на десктопе всё видно сразу.
Format: таблица «ширина → раскладка → ширина основной колонки», затем Tailwind-классы контейнера.
```

### 2.4. Плавающие и прилипающие элементы

```text
Role: ты — frontend-разработчик.
Task: на телефоне <плавающая кнопка «+» / прилипающая панель> перекрывает <суммы в списке / кнопку
«Сохранить»>. Предложи решение, при котором важный контент никогда не оказывается под ней.
Context: элемент position: fixed/sticky; есть вкладки; клавиатура телефона уменьшает высоту экрана.
Format: варианты (отступ снизу, скрытие по условию, sticky-подвал) с плюсами и минусами → выбранный код.
```

### 2.5. Проверка касаний и доступности на мобильном

```text
Role: ты — специалист по доступности (WCAG 2.2).
Task: проверь <компонент> на телефоне: размер целей нажатия (не меньше 44×44 px), видимый фокус,
контраст текста не меньше 4,5:1, работа с клавиатурой.
Format: таблица «элемент → проблема → класс Tailwind для исправления».
```

## 3. Рефакторинг

### 3.1. Разбить большой компонент

```text
Role: ты — senior React-разработчик.
Task: компонент <GroupPage.tsx> вырос до <340> строк. Выдели из него хуки и подкомпоненты так,
чтобы в странице остались только загрузка данных и раскладка. Поведение не менять, тесты должны проходить.
Context: правила проекта — CLAUDE.md (feature-based структура, логика в хуках и чистых функциях).
Format: план (что → куда → почему) → код новых файлов → изменённая страница → команда проверки.
```

### 3.2. Убрать дублирование стилей

```text
Role: ты — frontend-разработчик.
Task: найди в src повторяющиеся наборы классов Tailwind (фокус, кнопки-ссылки и т. п.), встречающиеся
3 и более раз, и вынеси их в общие константы. Новые зависимости не добавлять.
Format: таблица «набор классов → сколько повторов → имя константы» → изменения по файлам.
```

### 3.3. Отделить контракт API от mock-реализации

```text
Role: ты — архитектор фронтенда.
Task: типы и константы, которые UI импортирует из src/mocks (<ApiError, ExpenseInput, CURRENT_USER_ID>),
перенеси так, чтобы замена mock на <Supabase> затронула только реализацию API.
Format: новое расположение каждого символа → список изменённых импортов → проверка tsc.
```

### 3.4. Проверка асинхронного сценария на фейковых таймерах

```text
Role: ты — инженер по тестированию React (Vitest + Testing Library).
Task: напиши тесты для <отложенного удаления с отменой за 5 секунд>: запрос не уходит раньше срока,
уходит ровно в срок, не уходит после отмены, уходит сразу при уходе со страницы.
Context: vi.useFakeTimers, userEvent.setup({ advanceTimers }), mock-API без задержки.
Format: файл теста с путём → какие критерии приёмки он покрывает.
```

## 4. Отладка

### 4.1. Ошибка из консоли

```text
Role: ты — React-разработчик.
Task: в консоли браузера на странице <адрес> появляется: <полный текст ошибки или предупреждения>.
Объясни простыми словами, что она значит, найди причину в коде и исправь.
Format: что означает → где причина (файл:строка) → исправление → как убедиться, что сообщение ушло.
```

### 4.2. Тест падает только на другой ОС или иногда

```text
Role: ты — инженер по тестированию.
Task: тест <имя> <падает на Windows, проходит на Linux / падает примерно 1 раз из N запусков>.
Текст ошибки: <…>. Найди причину и исправь, не ослабляя проверку.
Context: частые причины — регистр в именах файлов, разделители путей, кодировка, гонки таймеров.
Format: причина → доказательство (как воспроизвести) → исправление → сколько повторных запусков прошло.
```
