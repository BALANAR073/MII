## 2. Что сделано хорошо

1. **Защита в БД продумана.** Есть RLS на всех таблицах и `revoke all` с точечными `grant`, в том числе по колонкам: чужой email не читается, `created_by` и `id` при вставке не подменить. Служебные функции вынесены в схему `private`. Во всех функциях `search_path = ''`, `security definer` RPC сами проверяют участие в группе, `alter default privileges` закрывает новые функции.
2. **Open redirect закрыт.** `safeNext` отбрасывает `//`, `\` и управляющие символы. Переход идёт через `<Navigate>`, то есть через `pushState`, а он в принципе не может увести на другой origin. OAuth работает по PKCE: в адресе только одноразовый `code`, токенов в истории и логах нет.
3. **XSS.** Нигде нет `dangerouslySetInnerHTML` и `innerHTML`, весь ввод выводится через JSX. CSP строгая: нет inline-скриптов, есть `object-src 'none'`, `frame-ancestors 'none'`, `base-uri` и `form-action`. Кроме того, выставлены HSTS, `nosniff` и `X-Frame-Options`, а smoke-тест проверяет, что заголовки реально приходят.
4. **Конвейер.** Actions закреплены по SHA, `permissions: contents: read`, выкладка идёт только из `main` через environment. Используются `npm ci` по lockfile и `npm audit --audit-level=high`. Подключены CodeQL и Dependabot, версия Vercel CLI зафиксирована.
5. **Логирование.** Принимается белый список полей, есть лимиты длины, размера и числа записей. Email, JWT и длинные токены вырезаются (32-символьный hex-токен приглашения под это правило попадает), query отрезается, есть проверка `Sec-Fetch-Site`. Пароли в журнал не пишутся.
6. **Секреты.** В бандл попадают только публичные URL и publishable-ключ, `.env*` в `.gitignore`, service_role нигде не используется. У Метрики выключен Вебвизор, цели передаются без сумм, имён и id.

## 3. Три самых важных исправления

1. **Утечка токена приглашения в Яндекс.Метрику (№1).** Не запускать счётчик на `/join/*` и `/auth/callback` или убирать токен из адреса до `initMetrika`. Вместе с этим добавить в интерфейс сброс ссылки (№5), чтобы уже утёкшие токены можно было отозвать.
2. **Ограничить `VERCEL_TOKEN` в CI/CD (№2).** Передавать токен только шагам с `vercel`, ставить зависимости с `--ignore-scripts`, хранить секрет в environment `production`, выпустить токен с узкой областью и сроком действия. Сейчас любая зависимость из npm может забрать доступ к аккаунту Vercel.
3. **Бизнес-правила переводов и расходов на сервере (№3, №4).** Переводы должен подтверждать получатель, а у участников должна быть возможность оспорить расход, записанный на них. Иначе должник может в одностороннем порядке и необратимо списать долг, а недобросовестный участник может не дать другим выйти из группы.

## 4. Итоговая оценка: 7/10

Основа сильная. Права в Supabase, на которых держится вся защита данных, сделаны тщательно: точечные гранты, права на колонки, `private`, `search_path`. Плюс строгая CSP с заголовками, PKCE, корректный `safeNext` и закреплённые по SHA actions. Критических уязвимостей, то есть чтения или изменения чужих групп без приглашения, я не нашёл.

Оценку снижают три вещи:
- реальная утечка токена-приглашения третьей стороне, которая противоречит политике конфиденциальности;
- слишком широкая доступность деплой-токена в CI;
- бизнес-логика «на доверии»: один участник может без согласия других менять их балансы, причём необратимо.
