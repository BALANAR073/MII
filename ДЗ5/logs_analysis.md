## 1. Промпт для анализа

```text
Role: ты — SRE-инженер, разбираешь логи Supabase (API Gateway + Postgres) и клиентский журнал веб-приложения.
Task: по выписке логов определи: 1) какие ошибки ожидаемы (негативные тесты, проверки прав), а какие —
признак проблемы; 2) для каждой группы ошибок — причину и слой (клиент, PostgREST, RLS, триггер, RPC, Auth);
3) есть ли признаки атаки или утечки; 4) что исправить и что добавить в мониторинг.
Context: проект «ПоРовну» на Supabase; в 19:49 и 20:03 запускались e2e-тесты (31 проверка, из них 13
негативных); в 19:37 вручную запускался deploy.sql в SQL Editor.
Format: таблица «время/шаблон → кол-во → слой → причина → ожидаемо? → действие», затем выводы.
```

## 3. Выводы

1. **Все 4xx объясняются** негативными проверками e2e и ожидаемым поведением прав. Ошибок 5xx нет.
2. **Одна находка безопасности** — подбор пароля к Postgres в первые минуты жизни проекта. Публичный адрес базы Supabase находят боты. Защищают длинный случайный пароль и то, что приложению прямое подключение не нужно.
3. **Подсказки PostgREST могут быть вредными.** На `permission denied` он советует «GRANT SELECT … TO anon». Выполнить это — значит открыть все группы гостям. AI-агент должен отличать «ошибку» от «сработавшей защиты».
4. **Что добавить в мониторинг (ДЗ6):** алерт на рост 5xx, на всплеск `FATAL password authentication failed`, на рост 401 после релиза (признак сломанного обновления токена).

Готовые промпты и команды для таких разборов — в `backend_diagnostics.md`.
